# Call Me Maybe

## Description

Call Me Maybe is a Python function-calling project based on the Qwen3-0.6B language model and the provided `llm_sdk`. It reads natural-language requests and function definitions, chooses a suitable function, and extracts its typed arguments. The application writes one JSON output file with the original prompt, function name and parameters.

**Project status:** This branch experimentally builds an argument dictionary incrementally, generating one primitive value at a time. Function-name selection is constrained; argument values still use greedy token choice and post-generation type validation. **Token-level value constraints are not yet implemented, so this prototype does not satisfy the subject's full constrained-decoding requirement.** The JSON structure is assembled with Python rather than generated by the LLM.

## Instructions

Requires Python 3.10+ and [uv](https://docs.astral.sh/uv/).

Install the dependencies:

```bash
make install
# or: uv sync
```

Run with the default input files:

```bash
make run
# or: uv run python -m src
```

Provide alternative input/output paths:

```bash
uv run python -m src \
  --functions_definition data/input/functions_definition.json \
  --input data/input/function_calling_tests.json \
  --output data/output/function_calls.json
```

The output file defaults to `data/output/function_calls.json`. It is created by the program.

Other Makefile targets: `make debug`, `make clean`, `make lint` and optional `make lint-strict`. The lint target runs flake8 and mypy with the flags required by the subject. Lint dependencies are installed transiently with `uv run --with`; `uv sync` remains the runtime setup.

## Algorithm

1. Read function definitions and prompts as JSON, then validate input objects with Pydantic.
2. Build the Qwen/Hermes function-selection context listing the available function schemas.
3. Encode available function names and choose the next token among their allowed token-ID prefixes, using the logits returned by the SDK.
4. Build one argument context, then extend its JSON prefix with already generated dictionary entries and the next required key. Generate that primitive value using the SDK, decode it with Python's JSON decoder, and check the declared type. Numeric values wait for a terminating separator so that the prefix `2` does not prematurely stop a longer value such as `265`.
5. Assemble the dictionary in Python and serialize the validated `FunctionCall` objects into one JSON array. Model-generated text never supplies the dictionary keys or separators.

**Remaining work:** Restrict the logits for each primitive type **before token selection**, handle invalid/unfinished strings robustly, and measure end-to-end accuracy with Qwen3-0.6B. The JSON prefix is built using `json.dumps(partial_dict)[:-3]`, not `str(dict)`. The separate JSON structure parser is not used by this experimental argument generator.

## Design decisions

- `ContextBuilder` assembles the language-model prompts.
- `FunctionSelector` selects only among the provided function names.
- `ArgumentGenerator` handles parameters one by one, rebuilding a consistent JSON prefix using the values already stored in its Python dictionary.
- `JsonGrammar` and `JsonStringParser` remain in the repository from the original branch but are not called by this alternative generator.
- Pydantic models validate input and output structures. The `Small_LLM_Model` wrapper is used through its public methods.

## Example usage

Example natural-language request:

```text
What is the sum of 2 and 3?
```

Expected output shape (illustrative, not a recorded model result):

```json
[
  {
    "prompt": "What is the sum of 2 and 3?",
    "name": "fn_add_numbers",
    "parameters": {"a": 2.0, "b": 3.0}
  }
]
```

## Testing strategy

Run the JSON grammar unit tests:

```bash
uv run python -m unittest discover -s tests
```

Run `make lint` for style and static type checks. Then execute the model against the supplied example inputs and additional, changed function sets. Inspect each output file for valid JSON, exact required keys, schema-compatible parameter types and correct extracted values. Include string escapes, Unicode, missing files, malformed input, empty strings, negative and decimal numbers, boolean values and ambiguous prompts in manual tests.

**Current limitation:** Passing parser unit tests does not establish end-to-end accuracy or full constrained-decoding compliance.

## Performance analysis

The subject targets at least 90% correct function selection and argument extraction, 100% parseable schema-compliant JSON, and under five minutes for the complete evaluation prompt set. These targets have **not been benchmarked for this branch**. Generating values separately may increase the number of model invocations compared with generating all arguments in one sequence. JSON serialization guarantees object syntax for supported finite values, but does not by itself enforce the required constraints during LLM token selection.

## Challenges

- Qwen tokens can span multiple text characters, and UTF-8 characters may be split across tokens.
- JSON escapes such as `\u0041` must be accepted as incomplete prefixes until all four hexadecimal digits are present.
- Numeric values require a reliable end-of-value rule.
- The current per-value post-generation validation cannot substitute for excluding invalid token IDs during generation.
