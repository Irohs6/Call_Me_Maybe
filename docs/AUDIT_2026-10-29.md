# Audit technique complet — Call Me Maybe

**Date :** 29 octobre 2026  
**Dépôt :** [Irohs6/Call_Me_Maybe](https://github.com/Irohs6/Call_Me_Maybe)  
**Branche analysée :** `test-json-structure-methods` (37 commits devant `main` au moment de l'inspection)  
**Référence de travail :** sujet `docs/subject_en.md`, version 1.7  
**Statut :** audit de code et des résultats de tests fournis par l'utilisateur ; **pas de certification de réussite du rendu 42**.

> **Périmètre et limites :** audit à partir des fichiers distants de la branche, des consignes du sujet et de deux exécutions réelles communiquées dans la conversation. Le dépôt local de l'utilisateur affiche `*` (modifications non commitées possibles) : les résultats locaux peuvent donc diverger de la version GitHub. Les tests unitaires complets, `make lint` et le modèle Qwen n'ont **pas été exécutés par l'auditeur** ; les constats dynamiques cités ci-dessous proviennent exclusivement des sorties fournies par l'utilisateur. Les risques non reproduits sont identifiés comme tels.

## 1. Verdict et synthèse

Le projet comporte un pipeline réellement fonctionnel : définition des fonctions -> validation Pydantic -> contexte Qwen -> sélection contrainte d'une fonction -> génération d'arguments avec vérification de préfixe JSON/schéma -> sortie au format demandé.

**Observations sur les deux séries fournies :** 22 prompts traités, 22 noms de fonctions apparemment corrects, 20 appels avec des arguments sémantiquement conformes aux prompts (90,9 %), 22 objets produits dont les clés et types semblent conformes aux deux schémas de test. Les deux erreurs observées portent sur la **fidélité des chaînes** (antislash/tabulation ; guillemets supprimés). Chaque série de 11 prompts a pris plus de 3 min 30 sur la machine de test. Ces chiffres ne garantissent **ni** 90 % sur les jeux cachés **ni** 100 % de JSON produit pour toute entrée **ni** moins de cinq minutes sur le jeu de correction.

**Verdict rendu :** **non prêt à certifier en l'état**. Les écarts de dépôt/documentation et de lint sont directement vérifiables ; les risques fonctionnels et de performance demandent des essais ciblés. Priorité : vérifier le pipeline avec de nouveaux jeux, corriger les écarts obligatoires de soumission, puis effectuer des benchmarks et la validation statique.

## 3. Architecture : audit par composant

### 3.1 `src/model/models.py` — schémas

**Points positifs :** modèles Pydantic simples, `extra="forbid"` sur les définitions et `FunctionCall`, liste de paramètres déclarés par fonction.

**Réserves :**
- `Type.type: str` accepte toute chaîne (« integer », « boolean », mais aussi « matrix », « booléen », etc.) ; le refus intervient tard dans le générateur. Préférer validation explicite à l'entrée lorsque les types autorisés du sujet sont connus.
- Pas de validation de l'unicité des noms de fonctions dans la liste ; le sélecteur construit un `dict` indexé par `function.name`, susceptible d'écraser une définition en doublon.
- Pas de vérification transversale des caractères/noms de paramètres et des descriptions vides ou incohérentes au niveau de la collection ; à tester sur fichiers alternatifs.
- `FunctionCall.parameters: dict[str, Any]` sert à la sérialisation ; la vérification métier est faite avant dans `ArgumentGenerator`, ce qui est cohérent, mais ce modèle seul ne garantit pas le schéma dynamique.

### 3.2 `src/model/parser.py` et `src/model/app.py` — entrées

**Points positifs :** lecture UTF-8, `with` pour fermer les fichiers, `FileNotFoundError`, `JSONDecodeError`, `UnicodeDecodeError`, validation des listes et objets par Pydantic.

**Réserves :**
- `JsonParser` remplace les erreurs Pydantic par un message générique (`Invalid function definition.` / `Invalid prompt definition.`), perdant l'emplacement précis de l'erreur utile à l'évaluation.
- `PermissionError` et autres `OSError` ne sont pas normalisées. Les fonctions en doublon, liste vide et schémas de types inconnus méritent des tests.
- La validation des définitions se limite à chaque objet ; la cohérence globale des fonctions n'est pas contrôlée.

### 3.3 `src/model/context_builder.py` — prompts Qwen

**Points positifs :** deux contextes explicitement séparés pour les deux tâches : sélection de la fonction et génération de tous ses arguments ; outil décrit avec `properties` et `required` ; `json.dumps(ensure_ascii=False)`.

**Réserves :**
- Les consignes de génération sont textuelles, donc elles **ne garantissent pas la fidélité sémantique** des valeurs, même avec un JSON toujours valide.
- Les instructions « Translate symbol names » et « use a pattern matching that class » sont utiles pour certains prompts, mais peuvent interférer avec la copie littérale de guillemets/antislashs. **Hypothèse à tester**, pas une cause démontrée des deux anomalies.
- Le contexte s'arrête après `"arguments": {` ; la logique du générateur préfixe le texte décodé par `{`. Cette convention doit rester synchronisée lors de tout refactoring.

### 3.4 `src/function_selector.py` — choix de fonction

**Points positifs :** noms disponibles encodés en séquences de tokens ; filtrage des IDs permis à chaque position ; choix du meilleur logit **parmi les IDs permis** ; aucune heuristique de recherche du nom dans le prompt.

**Réserves / tests manquants :**
- Aucun test unitaire dédié au sélecteur n'a été trouvé dans les fichiers inspectés.
- Des noms identiques s'écrasent dans le dictionnaire de candidats.
- Vérifier les noms partiellement communs, noms très longs, noms Unicode, noms inhabituels et liste de fonctions vide.
- Vérifier sur modèle réel les différences possibles entre la tokenisation d'un nom isolé (`function.name + "\n"`) et celle après le préfixe du contexte.

### 3.5 `src/json_checker.py` — validateur de préfixes

**Points positifs :** états explicites, helpers `is_*` / `read_*`, gestion de chaînes JSON et de `\uXXXX`, nombres avec signe/fraction/exposant, entiers sans décimales, booléens minuscules, noms/types des clés, rejet des doublons et des fermetures prématurées. `status()` renvoie `0` / `-1` / `-2`, adapté au constrained decoding.

**Réserves :**
- `is_key_prefix()` coupe au premier antislash (`key.split("\\", 1)[0]`) pour ne pas rejeter trop tôt une clé échappée. C'est prudent, mais **non exhaustif** : un préfixe impossible après un échappement peut rester `-1` jusqu'au guillemet final. La fermeture vérifie néanmoins le nom décodé.
- `status()` instancie et appelle directement les parseurs `JsonStringParser`, `JsonNumberParser` et `JsonBooleanParser` ; les méthodes `check_string`, `check_number` et `check_boolean` relancent elles-mêmes la lecture et ne sont pas utilisées par `status()`. Cela duplique une partie de l'interface. Refactor facultatif ; **ne pas refaire l'architecture sans besoin mesuré**.
- `json.loads` est employé pour décoder une clé **complète** ; c'est cohérent. Un préfixe doit en revanche rester contrôlé caractère par caractère.
- Le coût du contrôle d'un candidat est proportionnel à la longueur du JSON déjà généré : `status()` reparcourt toute la séquence. Risque de coût cumulatif dans la boucle de vocabulaire.
- Vérifier davantage les noms de clés avec guillemets, antislashs, caractères Unicode de substitution, tabulations échappées et caractères non ASCII.

**Note sur les tests :** un test Unicode avait échoué car il contenait **deux antislashs** dans une chaîne Python brute (`r'{"\\u006eame":...}'`) au lieu d'un ; ce test a été corrigé sur GitHub. La **réexécution après cette correction n'a pas été fournie**.

### 3.6 `src/argument_generator.py` — constrained decoding

**Points positifs :** construction du `JsonChecker` à partir du schéma de la fonction ; chargement du vocabulaire via une méthode publique du SDK ; lecture des logits ; exclusion des tokens produisant le statut `-2` ; terminaison sur statut `0` et validation du dictionnaire ; traitement immédiat des fonctions sans paramètres ; génération des paramètres en une passe.

**Points à surveiller en priorité :**
1. **D1 — Unicode fragmenté (`L112-L128`).** Le code rejette tout décodage intermédiaire contenant le caractère de remplacement `\ufffd`. Quand le tokenizer nécessite plusieurs tokens pour produire un seul caractère UTF-8, le premier préfixe peut être rejeté, bloquant toute la séquence pourtant valide à la fin. C'est un risque avéré dans la logique, à reproduire sur vrais tokens.
2. **P1 — temps (`L94-L128`).** Pour **chaque prompt**, le générateur recharge `vocab.json`. Pour **chaque token généré**, il trie *tous* les IDs du vocabulaire selon les logits, puis peut appeler `model.decode(generated_ids + [id])` et `checker.status("{" + text)` pour de nombreux candidats. Cela génère des coûts importants ; profiler les appels avant de changer l'architecture.
3. **Fin de génération (`L108, L138-L142`).** Limite fixe à 256 tokens. Toute entrée plus longue, modèle bloqué ou absence de continuation valide entraîne `ValueError` ; pas de résultat partiel ni de stratégie d'achèvement garantie. Tester les chaînes longues.
4. **Validité vs exactitude (`L132-L135`).** `JsonChecker` peut rendre un JSON structurellement correct tout en conservant un texte erroné dans une string ; la validation de types post-génération n'y remédie pas.
5. **Vocabulaire et spécial tokens.** Le code filtre les valeurs du JSON qui sont des entiers positifs, mais pas de tests directs avec IDs hors plage, IDs dupliqués, modèle/vocabulaire discordants, score `NaN`, caractères de remplacement et tokens spéciaux. Le filtrage `text == previous_text` exclut les tokens qui ne changent pas la chaîne décodée, ce qui est souhaitable pour beaucoup de tokens spéciaux, mais requiert des tests de tokenizer.
6. **Coût mémoire/temps des décodages.** Chaque candidat est décodé en repartant de tous les IDs précédents, avant de reparcourir toute sa chaîne par le checker. **Ne pas présumer** que décoder un token isolé puis concaténer est équivalent : le tokenizer peut découper les octets UTF-8 entre tokens.
7. **Validation finale.** `validate_arguments()` vérifie la correspondance exacte des noms, `string` / `number` / `integer` / `boolean` et convertit `number` en `float`. Ce filet de sécurité est utile ; conserver des tests pour `bool` vs `int` et clés supplémentaires.

**Option d'optimisation à évaluer, non implémentée :** charger le vocabulaire une seule fois par instance du générateur, utiliser une recherche progressive des meilleurs logits avec élargissement garanti jusqu'à trouver un token valide (sans couper arbitrairement aux seuls « top N »), mesurer les décodages et éviter les validations intégrales inutiles. Ne pas appliquer une optimisation sans benchmark ni tests de régression.

### 3.7 `src/__main__.py` et sortie

**Points positifs :** CLI avec les trois options requises, dossier de sortie créé automatiquement, fichier final sérialisé en JSON, modèle et sélecteur initialisés une fois par exécution.

**Réserves :**
- Le `try/except` capture `ValueError`, `FileNotFoundError` et `JSONDecodeError`, mais ni les erreurs de permission, ni les éventuelles exceptions de modèle/téléchargement, ni certains accès invalides. Le sujet insiste sur la gestion robuste des erreurs.
- L'exception est imprimée puis la fonction retourne, sans code de sortie non nul explicite. Une exécution défaillante peut ainsi être interprétée comme réussie par un script.
- Le fichier n'est écrit **qu'après** avoir traité tous les prompts : une erreur sur un prompt peut empêcher l'écriture de tous les résultats.
- `args.output.open("w")` n'explicite pas `encoding="utf-8"` ; point de portabilité.
- Ne pas confondre la demande de *traduire des prompts en appels* et l'exécution réelle de SQL/fichiers : ici les chaînes SQL et chemins sont uniquement sérialisés ; **aucune requête SQL n'est exécutée**.

### 3.8 `pyproject.toml`, `uv.lock`, `Makefile`, `llm_sdk/`

- `pyproject.toml` déclare Python >=3.10, numpy, pydantic et les dépendances nécessaires au SDK. `uv.lock` est présent ; `uv sync` doit être testé en environnement propre.
- `[tool.uv.sources]` force `torch` vers l'index `pytorch-cpu`. Cela peut limiter l'usage d'accélérateurs sur certaines machines ; **risque**, pas preuve de défaut sur la machine de test.
- `Makefile` expose les cinq cibles requises et les flags de mypy demandés. Cependant `flake8 .` vise aussi le SDK fourni.
- `llm_sdk/__init__.py` contient **14 lignes >79 caractères** et des imports apparemment inutilisés (`time`, `Tuple`, `os`). `flake8 .` est donc **susceptible d'échouer** (notamment E501/F401) tant qu'une vérification réelle et une stratégie conforme pour le SDK n'ont pas été faites.
- Les appels au wrapper par le projet semblent se limiter aux API publiques autorisées. Ne pas « réparer » automatiquement le SDK sans examiner ce qui est considéré comme fichier fourni immuable.

## 4. Résultats réels disponibles

Ces mesures sont **fournies par l'utilisateur**, sur sa machine ; elles ne sont pas une campagne automatisée indépendante.

| Série | Fonctions | Prompts | Sélections correctes apparentes | Arguments exacts apparents | Temps réel |
|---|---:|---:|---:|---:|---:|
| A — addition, salutations, reverse, racine, regex | 5 | 11 | 11/11 | **10/11** | **3 min 33,14 s** |
| B — multiplication, pair, intérêts, SQL, fichiers, templates | 6 | 11 | 11/11 | **10/11** | **3 min 36,63 s** |

**Erreurs fonctionnelles observées :**
- **A :** l'entrée comportant `'hel\\lo'` a produit une valeur interprétée comme `'hel\to'` (tabulation à la place des caractères originaux). L'écart est dans les données extraites, pas dans le type JSON.
- **B :** pour `Format template: Say "hello" to {name}`, la sortie était `Say hello to {name}` : les guillemets autour de `hello` ont disparu.

**Ce qui marche sur ces essais :** extraction de grands nombres, décimaux et entiers, booléens dans des appels, expressions regex, chemins Unix/Windows et clés de plusieurs paramètres. Ces succès ne couvrent pas tous les échappements et ne garantissent pas les fonctions cachées du correcteur.

**Interprétation temps :** chaque série est sous cinq minutes **individuellement**. Le sujet fixe « tous les prompts de test sous cinq minutes » ; on ne peut pas en conclure que le jeu du correcteur passe. Si un seul jeu comptait ces 22 prompts, la somme des deux chronos dépasse cinq minutes, mais ce n'est **pas** un benchmark réel d'une exécution unique des 22 prompts.

## 5. Tests : inventaire et trous de couverture

**Présents sur la branche :**
- `tests/test_json_checker.py` : **19 méthodes** pour strings, échappements, nombres, entiers, booléens, noms/types de clés, préfixes et structure.
- `tests/test_argument_generator.py` : **5 méthodes** avec faux modèle (`MagicMock`) pour sélection de tokens, types, absence de continuation et fonction sans argument.

**Résultats d'exécution attestés :** l'utilisateur a exécuté la suite JSON *avant la correction des quatre littéraux mal échappés* : 18 `ok`, 1 `FAIL`. Les fichiers ont été corrigés ensuite ; **aucune exécution des 24 tests sur la révision auditée n'a été communiquée**. Les cinq tests du générateur sont présents, mais leur réussite n'est pas prouvée ici.

**Manques à combler, ordonnés :**
1. Test réel et profilage sur jeux A/B et au moins un **troisième jeu inédit**, sans modifier le schéma à la main dans le code.
2. Tests de chaînes fidèles : `"hello"`, `'hel\\lo'`, guillemets littéraux, tabulations réelles, `\n`, `\uXXXX`, emoji, accents, caractères UTF-8 fragmentés entre tokens.
3. Tests du sélecteur avec noms similaires, dupliqués, non ASCII, noms longs et ordre de fonctions modifié.
4. Tests `JsonParser` et CLI : fichiers absents, JSON corrompu, tableau incorrect, type inconnu, permissions, chemin de sortie invalide, liste de fonctions vide.
5. Tests du budget de 256 tokens et des prompts volumineux.
6. Tests d'exception SDK et de récupération d'erreur sans traceback.
7. `make lint`, éventuellement `make lint-strict` et `uv sync` dans un environnement vierge ; conserver le journal de résultats.
8. Non-régression sur deux versions des jeux de définition pour détecter un surapprentissage des exemples.

## 6. Qualité, lisibilité et maintenabilité

**Points positifs :**
- Architecture lisible en trois étapes : `ContextBuilder`, `FunctionSelector`, `ArgumentGenerator` ; validation des entrées/sorties distincte.
- Utilisation cohérente des modèles Pydantic dans le code métier.
- Helpers d'états nommés dans le checker ; choix des tokens contraint pendant la génération, pas simple réparation du JSON final.
- Sélection de fonction par score LLM et non par règles ad hoc sur les mots du prompt.

**Améliorations mesurées :**
- `src/json_checker.py` approche **587 lignes** et contient quatre classes, dont une orchestration de statut et trois analyseurs de valeurs. Ce n'est pas un défaut fonctionnel à lui seul ; il faut limiter les méthodes de façade inutilisées avant de rajouter des couches.
- `check_string` / `check_number` / `check_boolean` existent mais `status()` ne les utilise pas. Décider si elles sont des API utiles à tester ou supprimer la duplication **après discussion**.
- Un seul test numérique à format « float » ne suffit pas pour conclure sur toutes les représentations Unicode, exponentielles et de grandes valeurs.
- Tester statiquement `mypy` : certains rétrécissements de type (via variable booléenne `valid` avant un `float(value)`) méritent confirmation plutôt que supposer la réussite.
- Mettre à jour le README avec des mesures documentées et les limites établies, sans présenter les essais comme un score officiel 42.
