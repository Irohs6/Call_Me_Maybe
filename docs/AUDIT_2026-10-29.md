### Point d'attention : le SDK et les dépendances

- `llm_sdk/__init__.py` fait des imports directs de `torch`, `transformers` et `huggingface_hub`.
- `llm_sdk/pyproject.toml` déclare effectivement `torch>=2.0.0`, `transformers>=4.40.0` et `huggingface-hub>=0.20.0`. **Mais la présence de ce `pyproject` dans un sous-dossier ne l'intègre pas automatiquement comme dépendance au projet racine.**
- `pyproject.toml` racine déclare `llm_sdk`, `numpy`, `pydantic`, `flake8`, `mypy` ; l'entrée `[tool.uv.sources] torch = ...` définit **une source si torch doit être résolu**, pas une dépendance.
- Le projet imbriqué `llm_sdk/pyproject.toml` se nomme même `call-me-maybe`, et non `llm_sdk` : il ne faut pas présumer qu'une dépendance PyPI `llm_sdk` installera correctement le wrapper copié.
- L'exigence du sujet est un `uv sync` autonome lors de la correction. **Vérifier en environnement propre et résoudre ce blocage explicitement.** Le sujet interdit l'utilisation directe de ces frameworks dans le code métier, mais le SDK fourni en dépend à l'exécution : ne pas confondre ces deux aspects.

## 3. Audit composant par composant

### 3.1 Entrées : `src/model/parser.py`

**Points solides :**
- Lecture en UTF-8 et fermeture automatique des fichiers.
- Messages pour absence de fichier, JSON malformé (ligne/colonne), UTF-8 invalide et autres erreurs système.
- Messages Pydantic réduits à leur premier diagnostic et contextualisés avec `Invalid function #N` / `Invalid prompt #N`.
- Vérification des noms de fonctions dupliqués et de la liste vide.
- **Dernière correction J3 :** `object_pairs_hook` refuse des clés JSON répétées **avant** que `json.load` écrase la première. Couvre aussi les niveaux imbriqués ; deux objets distincts peuvent avoir les mêmes noms de champs.

**Limites :**
- L'erreur `Duplicate JSON key: 'b'` mentionne le champ, mais pas encore le chemin complet (`functions[0].parameters.b`) ni sa ligne. C'est une **amélioration ergonomique**, pas un défaut bloquant.
- `_validation_message` ne restitue que **la première** erreur Pydantic, intentionnellement ; pratique pour le terminal mais moins exhaustif pour diagnostiquer plusieurs champs.
- `json.load` de Python accepte des constantes non standard `NaN` / `Infinity` par défaut ; les schémas actuels devraient en rejeter la plupart aux endroits typés, mais une politique JSON strict explicite est préférable.

### 3.2 Modèles : `src/model/models.py`

**Points solides :** Pydantic avec `extra="forbid"`, refus des noms de paramètres vides, des types d'arguments étrangers et des champs supplémentaires, contrôle des chaînes vides pour nom/description/prompt.

**Limites :**
- `Type.type: str` n'impose pas de liste fermée pour le champ `returns`, contrairement aux paramètres. **Ne pas le resserrer sans vérifier les types de retour admissibles par les tests du sujet.**
- `FunctionCall.parameters: dict[str, Any]` ne garantit pas à lui seul le schéma dynamique : cela repose sur `ArgumentGenerator.validate_arguments`.
- `validate_arguments` convertit `number` en `float`. Les entiers trop grands peuvent lever une exception à cette conversion ; les flottants non finis restent acceptés (J1).

### 3.3 Contextes : `src/model/context_builder.py`

Deux contextes séparés et clairs : sélection parmi les fonctions disponibles, puis création de tous les arguments en une génération JSON. La structure décrit `properties` et `required`. Aucune heuristique de détection par mots-clés n'a été observée.

**Risque :** les consignes de copie de texte restent un prompt et ne peuvent garantir l'exactitude des guillemets, antislashs ou caractères UTF-8, même si la structure produite est valide.

### 3.4 Sélecteur : `src/function_selector.py`

**Points solides :**
- Les noms de fonctions sont encodés par le SDK, avec `\n` terminal.
- À chaque étape, seul le meilleur logit parmi les tokens autorisés est accepté.
- Les fonctions en doublon sont rejetées dès la lecture du fichier.
- Nouvelles protections sur la liste de fonctions vide et les IDs de tokens hors plage.

**Limites :**
- Tests ajoutés seulement pour absence de candidats et ID invalide ; il manque des tests dédiés aux vrais noms qui se ressemblent, aux préfixes communs et aux tokenisations particulières.
- Pas de contrôle explicite de finitude des logits dans le sélecteur ; un `NaN` du SDK devrait être géré ou, au minimum, reproduit en test.
- Un échec de sélection provoque l'arrêt global du lot ; le message est maintenant contextualisé par numéro de prompt.

### 3.5 Checker : `src/json_checker.py`

**Points solides :**
- Automate explicite : clés requises en ordre libre, aucun doublon, structure JSON, nombres, booléens, chaînes et échappements `\uXXXX` ; `status` retourne `0`, `-1`, `-2`.
- Le numéro `integer` refuse la fraction et l'exposant ; `number` accepte les fractions et exposants.
- Les méthodes de façade redondantes `check_*` ont été supprimées ; les trois parseurs sont utilisés directement dans `status`.

**Limites :**
- `is_key_prefix` repousse certains rejets de clé après un antislash ; la fermeture de clé vérifie bien le vrai nom décodé, donc c'est surtout une occasion d'éviter du travail inutile.
- `status` recrée les parseurs et reparcourt toute la chaîne **pour chaque candidat testé**.
- Le checker valide la **forme lexicale** d'un nombre, pas le fait qu'il reste représentable par un `float` fini : J1.
- L'utilisation d'un préfixe Python décodé peut exclure des octets/tokenizations pourtant valides une fois complétés (D1).

### 3.6 Générateur : `src/argument_generator.py`

**Points solides :**
- Une génération unique pour l'ensemble des paramètres, contrôle à chaque token contre `JsonChecker.status`, puis `json.loads` et vérification de l'ensemble exact des clés et des types.
- Pas d'appel au modèle lorsque la fonction ne demande aucun argument.
- Cache `_vocabulary_ids`, filtrage des IDs non entiers/négatifs et des logits non finis, et `heapq` pour explorer les candidats par score.

**Points ouverts :**
1. **J1 — sérialisation de `Infinity`.** Le chemin `number` accepte `float('inf')`. `json.dump(..., indent=4)` utilise implicitement `allow_nan=True`, qui n'est pas du JSON standard. Le correctif devra rejeter les nombres non finis **et** forcer une sérialisation JSON stricte, avec test de régression.
2. **D1 — décodage UTF-8** : rejet systématique des chaînes décodées contenant `\ufffd`, potentiellement incorrect pour des caractères multi-tokens.
3. **P1 — temps** : la liste complète des candidats et le tas sont construits à chaque token ; le décodage et `status` réanalysent souvent le texte entier.
4. **Limite de 256 tokens** : `ValueError` sur sortie longue ; aucun mécanisme de reprise ni garantie d'achèvement.
5. **Nombres géants** : `float(value)` peut lever `OverflowError` pour un très grand entier ; ce cas devrait être validé et rapporté proprement.

### 3.7 CLI et erreurs : `src/__main__.py`

**Améliorations constatées :**
- Imports du SDK à l'intérieur du `try` : `ModuleNotFoundError` et `ImportError` obtiennent un message utilisateur plutôt qu'un traceback Python brut.
- Messages de lecture, génération (`Prompt #N`) et écriture ; échec retourne `1`, interruption clavier `130`.
- Couleur rouge sur `Error:` et verte sur `Dict answer final:` uniquement lorsque le terminal est interactif et ne porte pas `NO_COLOR`.

**Limites :**
- Le `try` par prompt **reformule l'exception mais ne continue pas au prompt suivant** ; c'est cohérent avec une stratégie *fail fast*, à assumer explicitement.
- L'écriture finale arrive après tous les prompts. Une erreur avant l'écriture peut **laisser sur disque un ancien fichier de résultat**, particulièrement gênant puisque `data/output/function_calls.json` est suivi par Git.
- L'écriture n'est pas atomique : si `json.dump` échoue après ouverture, le fichier peut être tronqué/partiel.
- Le `except Exception` terminal protège le CLI, mais peut masquer la nature d'une erreur de programmation ; conserver une voie de diagnostic en mode debug est préférable.

### 4.3 Reproduction du problème `Infinity` (effectuée)

Avec la bibliothèque standard de Python :
- `json.loads('{"value": 1e400}')` produit un `float` infini ;
- `json.dumps({"parameters": {"value": float("inf")}})` écrit `Infinity` ;
- `json.dumps(..., allow_nan=False)` rejette la valeur.

Le validateur actuel accepte une valeur de type `float` sans `math.isfinite`, et l'écriture n'active pas `allow_nan=False`. C'est une **faille démontrée dans la garantie de JSON strict, sous condition que le LLM produise cette valeur** ; aucune sortie réelle de Qwen avec `Infinity` n'est alléguée.
