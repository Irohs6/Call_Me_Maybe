## 3. Architecture et code relus

### 3.1 Modèles et parser — `src/model/models.py` / `parser.py`

- `Function`, `Prompt`, `Type` et `FunctionCall` sont basés sur Pydantic.
- Le validateur `Function.check_parameters` vérifie les quatre types d'arguments `string`, `number`, `integer`, `boolean` et refuse les noms vides ou composés d'espaces.
- `JsonParser.load_functions` refuse les définitions de fonctions vides et les noms de fonctions dupliqués ; les erreurs de validation Pydantic conservent désormais leurs détails.
- **Limites :** `Type.type` reste un `str` libre pour le type de retour ; contraintes globales des définitions et traitement des erreurs d'accès aux fichiers à vérifier sur d'autres jeux.
- Le modèle de sortie `FunctionCall.parameters` est un `dict[str, Any]` : l'assurance du schéma dynamique dépend des validations réalisées pendant/après la génération.

### 3.2 Construction des contextes — `src/model/context_builder.py`

- Un contexte est consacré au choix de fonction, un autre à la génération groupée de tous les arguments d'une fonction.
- Les définitions des outils décrivent les noms et types des paramètres.
- **Limite :** les consignes textuelles de copie n'assurent pas la préservation parfaite des caractères dans les valeurs, comme les échecs passés le montrent.
- La génération de l'objet argument est synchronisée avec le contexte qui se termine avant ce JSON ; toute modification du préfixe doit être testée avec le générateur.

### 3.3 Sélection de fonction — `src/function_selector.py`

- Contraint chaque token à un préfixe du nom des fonctions disponibles ; sélection selon les logits du LLM, non selon un rapprochement heuristique.
- Les doublons de noms sont maintenant rejetés à l'entrée du programme, avant le dictionnaire interne du sélecteur.
- **Tests à ajouter :** noms partageant des préfixes, noms Unicode, longueurs variables, fonction sans paramètres, jeu de fonctions modifié ou ambigu.

### 3.4 Vérification JSON — `src/json_checker.py`

- `JsonChecker.status()` renvoie `0` (complet), `-1` (préfixe autorisé), `-2` (invalide).
- Parseurs spécialisés `JsonStringParser`, `JsonNumberParser` et `JsonBooleanParser` ; états explicites, validation des clés requises, des types et des échappements de chaînes.
- **Q1 corrigé :** les trois façades `check_*` redondantes ont été retirées ; `status()` utilise toujours les parseurs réels.
- **Limites :** `is_key_prefix` coupe au premier antislash pour reporter le rejet d'un préfixe potentiellement échappé ; `status()` reparcourt tout le texte pour chaque candidat et doit être profilé.

### 3.5 Générateur — `src/argument_generator.py`

- `ArgumentGenerator` crée le checker à partir de la fonction choisie, puis génère tous les paramètres sous forme d'un JSON unique.
- **P1 appliqué :** le vocabulaire n'est plus relu par prompt dans la même instance (`_vocabulary_ids` via `PrivateAttr`) ; `heapq.heapify` puis `heapq.heappop` sélectionnent les candidats par logits décroissants ; les logits non finis sont filtrés.
- **P1 restant :** construction d'une liste de tous les candidats et du tas à chaque token, et potentiellement beaucoup d'appels `model.decode` et `checker.status`, lequel vérifie l'objet entier. Les résultats d'une seule exécution ne suffisent pas à isoler le gain dû à P1.
- **D1 restant :** `"\ufffd" in text` exclut un token pouvant être seulement le début d'une séquence UTF-8 fragmentée.
- **D2 restant :** la validité JSON/les types n'assurent pas la fidélité de `"hello"` ou des antislashs d'un prompt.
- **Limite fixe :** génération bornée à **256 tokens** ; comportement à tester sur longues chaînes ou nombreux paramètres.
- La validation finale vérifie les clés attendues et les types. Ne pas remplacer une génération contrainte par un simple parsing/rattrapage final.

### 3.6 Point d'entrée, sortie et erreurs — `src/__main__.py`

- Paramètres CLI `--functions_definition`, `--input`, `--output` ; le fichier est écrit en UTF-8 après génération.
- **E1 appliqué :** `main()` retourne désormais `0` si le traitement réussit et `1` sur une exception, avec message sur stderr ; le test simulant une erreur système passe.
- **Limite :** toutes les sorties ne sont sérialisées qu'après le dernier prompt ; si l'un échoue, l'exécution se termine sans livrer le tableau complet. Pas de benchmark d'erreurs SDK ou réseau en conditions réelles. `KeyboardInterrupt` n'est pas un `Exception` et n'est pas couvert par ce bloc.

### 3.7 Dépendances, Makefile, README et dépôt

- `pyproject.toml` dépend du paquet `llm_sdk`, ainsi que de `numpy`, `pydantic`, `flake8` et `mypy`. `uv.lock` présent. Une exécution `uv sync` récente a réussi sur la machine de l'utilisateur, sans constituer un test d'installation vierge.
- Le Makefile actuel :
  - `lint` : `flake8 src`, puis Mypy sur `src` avec les options de typage prescrites et `--follow-imports=silent` ;
  - `lint-strict` : `flake8 src`, puis `mypy src --strict --ignore-missing-imports --follow-imports=silent`.
- Le retour de `make lint-strict` est **réussi (10 fichiers)**, mais la commande ne vérifie pas automatiquement le contenu de `llm_sdk/`, `docs/` ni `tests/`.
- **README :** le texte dit encore que les méthodes `check_string` / `check_number` / `check_boolean` sont disponibles alors qu'elles ont été supprimées. L'ancienne référence de branche et la stratégie `uv --with` sont également devenues obsolètes.
- **Rendu :** `data/output/function_calls.json` est encore présent dans les fichiers suivis sur `main` ; le dossier doit être retiré de l'index avant soumission.
